# Clipping: a component cannot paint outside its own rect

Status: implemented
Date: 2026-08-25
Issue: [#357](https://github.com/WonderForgeLabs/gooey/issues/357)

## The problem

There was no clipping anywhere in gooey. `render.Buffer.Set` bounds-checked
against the *screen* — `b.W`/`b.H` — and nothing between `Render` and the
cell array knew where the painting component had been arranged. Any
component could write any other component's cells.

The reason that is worse than a rendering artifact is damage tracking. A
stray write lands in cells whose owner is **clean**: its paint node did not
invalidate, so it will not repaint, so nothing ever paints over the
corruption. It persists until something unrelated dirties the victim. The
symptom, seen from the far end, is "stray characters in a pane that never
fixes itself".

It also blocked a whole class of component. A framework-level viewport —
`<ScrollViewer>`, or any container showing a window onto oversized content —
could not be built, because a child arranged partly outside does not render
imperfectly, it corrupts its neighbours. `ItemsView` is a viewport
*precisely because it virtualizes*: it never arranges a row that would fall
outside, so it never needs to clip. Virtualization was not an optimization,
it was the only way to have a viewport at all
(`docs/specs/2026-08-23-scrolling.md` records that being rediscovered).

## The decisions

**Where the rect lives: on the Buffer, installed by the Composer.**

`Frame.Cells` is a public field and every component paints through
`f.Cells.Set`. A clip on `Frame` would not be enforced without making
`Cells` private and routing every write through a method — an API break
touching every component in the tree. Putting it on the Buffer clips every
existing call site with no component changes at all.

The Composer brackets `Render` with `Clip`/`Unclip`, in exactly the place
it already saves and restores the graphics `sink`. Both answer the same
question — "which component is painting right now" — and both have the same
hazard: a Render that evaluates another node would otherwise leave the wrong
answer installed.

**Framework-wide, not opt-in, because it is free.**

`Clip` intersects with the buffer, so the clip is always inside it. That
invariant lets `Set` test the clip *instead of* the buffer rather than as
well as it: four comparisons, exactly as many as bounding to the screen
already cost.

Measured with both arms writing the same cells, so the only difference is
which four values the comparison uses:

```
BenchmarkBufferSetClipped-22      5000000    15.88 ns/op
BenchmarkBufferSetUnclipped-22    5000000    15.59 ns/op
```

An earlier version of that benchmark let the clipped arm write across the
whole buffer, so most of its writes were rejected and it skipped the cell
store — it came out twice as *fast*, measuring "a rejected write is cheap"
rather than the cost of the check.

Since it costs nothing, opt-in would have bought nothing and left the
silent-corruption class alive for everyone who did not opt in.

**`Clip` intersects; it never replaces.** Nesting can only narrow, so a
component cannot widen its way out to a neighbour's cells by clipping to
something larger than it was given. `Unclip` is a separate method for the
restore, which must *not* intersect.

**Graphics placements are clipped against the same rect.** A clip covering
text and not pictures would be worse than none, because it would look like
it works right up until a component with an image overflowed — and a sixel
or kitty image is composited by the terminal, so no cell-plane check can
catch it. `Frame.Place` trims the placement's cell rect and crops the image
to match; the image was rasterized for exactly `Cols`×`Rows` cells, so cells
map to pixels by a plain ratio. A partly-visible image is **cropped, not
dropped** — a row scrolling off the top of a pane should lose its top half,
not vanish. An image whose type cannot be cropped is dropped, because losing
a picture is visible and local whereas letting it composite over a neighbour
is the silent corruption this exists to prevent.

## What it cost

Nothing moved. The full root suite passes, including roughly 141 exact
damage-count assertions — the contract tests that would have caught a
changed subscription or an extra repaint — and all 25 nested modules pass,
including every `apps/*` and the whole `-race` tier.

That no component anywhere in the tree was painting outside its bounds is
worth stating plainly: the bug was a missing guard rather than an active
corruption, and the guard is now closed before anything grew to depend on
its absence.

## What it enables

A container may now arrange a child partly outside itself and paint it. That
is the precondition for `<ScrollViewer>`, for a scrolling code surface
([#225](https://github.com/WonderForgeLabs/gooey/issues/225)), and for any
canvas with a viewport. Virtualization remains the cheaper answer where the
content is a uniform list — it avoids the work rather than discarding it —
but it is no longer the *only* answer.

## What is pinned

- `TestAComponentCannotPaintOverItsNeighboursCells` — the acceptance case.
  The overflowing component paints **backwards**, into a neighbour that
  already painted. That direction is load-bearing: document order is paint
  order, so a component overflowing *forward* is painted over by the
  neighbour it corrupted, and the first version of this test asserted
  exactly that and passed with the clip removed.
- `TestClipOnlyEverNarrows` — a second `Clip` cannot widen the region.
- `TestAPlacementIsClippedToItsComponentToo` — the pixel plane, in cells
  and in pixels.
- `TestTheClipIsRestoredAfterEveryRender` — the opposite failure. The
  Composer's own writes (pre-clears, `restoreUnder` sweeping a vacated
  overlay rect) happen outside any `Render` and legitimately touch cells
  anywhere; leave a component's clip installed and they are silently
  dropped, so a vacated popup never gets cleaned up.

Each was verified against its own mutant: with the cell clip reverted the
first two fail, and with the `Frame.Place` clip removed the third fails.
