# Input round 2: capture, CanExecute, tunneling, selection (epic [#31](https://github.com/WonderForgeLabs/gooey/issues/31))

The gaps named by the "same semantics as modern XAML?" audit, now due.

## Mouse capture

Press captures: from MousePress on a component until release, ALL
pointer events route to the captured component regardless of hit —
drag continues outside bounds, release is delivered to the captor
(click synthesis keys off captor identity, replacing press+release-
same-target). Explicit API too (CaptureMouse/ReleaseCapture on the
FocusManager) for components that capture without a press. Hover
transitions suppressed while captured. This is what scrollbar thumbs,
splitters, and drag interactions need; Button's slide-off-and-back
behavior becomes correct automatically.

## CanExecute as a computed

`Command` stays func(). New `Commands` are built with
`gooey.NewCommand(run).When(canExec *prop.Property[bool])` (shape
negotiable — typed, no reflection). A Button whose command has a When
reads it while painting (disabled style, another paint dependency) and
refuses activation when false. Markup unchanged: the binding resolves
the richer command transparently. The graph IS CanExecuteChanged — no
event, no manual invalidation, the audit's "arguably cleaner than
XAML" claim made real. KeyBindings honor When too.

## Tunneling

Before target-then-bubble, walk root→target offering the event to
ancestors implementing PreviewKeyHandler/PreviewMouseHandler (or one
Preview interface with both). First consumer stops the descent. This
is the parent-veto mechanism: modal scrims, masked inputs, the
browser's future overlay. Dispatch order becomes: tunnel down →
target → bubble up → bindings-per-level as today → app fallbacks.

## TextBox: mid-string editing and selection

Caret movement (left/right/home/end, word-wise with ctrl), insertion
and deletion at the caret, a selection anchor (shift+movement),
selection rendering (reverse), cut/copy behavior LOCAL only (kill
buffer, no OSC 52 this pass — note as future), horizontal scroll
keeping the caret visible. Mouse: click places the caret, drag selects
(the capture machinery's first consumer), double-click selects a word.

## Double-click

MouseClick gains a click-count (interval-based, 400ms default);
double-click is click-count 2 — ItemsView's Activate accepts it, and
TextBox uses it for word selection. No triple-click this pass.

## Acceptance

Damage discipline throughout (disabled-state flips repaint one
button; caret movement repaints one component). Unit tests per
mechanism; capture and drag proven with synthesized event sequences;
TextBox editing pty-smoked in finder. All demos keyboard-identical.

## Executed

Shipped as specified, landed in [PR #86](https://github.com/WonderForgeLabs/gooey/pull/86), with these decisions made along the way.

**`gooey.Action` is the field type.** `Command` had to stay `func()`,
and a func cannot carry a condition, so the event fields (`Button.Click`,
`KeyBinding.Command`, `ItemsView.Activate`, `TextBox.Changed`,
`Timer.Tick`) are typed as an interface with `Run()` and
`CanExecute()`. `Command` is a named func type, so it carries those
two methods itself and every existing delegate satisfies the interface
unchanged; `*Cmd` from `NewCommand(run).When(cond)` is the other
implementation. `gooey.CanExecute(a)` is the nil-tolerant form, because
an unset field is a nil interface. `Cmd.Run` is itself a no-op while
the condition is false, so "disabled" is structural rather than a rule
each caller must remember. The only source churn was bare `func()`
literals assigned to those fields, which now need the `gooey.Command`
conversion they always could have had.

**Dispatch order keeps bindings interleaved.** The spec's "tunnel down →
target → bubble up → bindings-per-level as today" is implemented as
tunnel, then the existing bubble with bindings-before-handler at each
level. Hoisting all bindings into one pass after the bubble would have
changed which of an ancestor's binding and a nearer ancestor's
`HandleKey` wins, and that ordering is what scopes a control's gestures.
Tunnelling is therefore purely additive: nothing that worked before
routes differently.

**Click synthesis asks whether the pointer is still inside the captor**
(the captor or a descendant), not merely that a captor exists.
Unconditional synthesis on release would fire a button the user pressed
and then deliberately released elsewhere, which is the one thing
press-and-drag-away is for. Implicit capture is scoped to one
press-release pair and a new press ends it — the recovery path for a
release the terminal never sent, which would otherwise strand the
pointer forever.

**Hover is frozen, not cleared, while captured.** A button being dragged
within itself keeps its hover visual; on release, hover catches up with
where the pointer actually is.

**`ctrl+c` in a TextBox is only consumed when there is a selection.**
The framework quit key is `ctrl+c` and it is checked on what bubbles out
of the tree, so an unconditional copy would make every focused field
swallow quit. Cut/copy/paste use a process-local kill buffer
(`components.KillBuffer`); OSC 52 remains future work, and deliberately
so — it is write-only on most terminals, off by default in several, and
a genuine exfiltration vector.

**`render.Style` gained `Dim`** (SGR 2, both in the ANSI encoder and the
model screen). A disabled button needed a visual and dim is the terminal
convention for one.

Two existing tests changed. `TestReaderShapeClickAndWheelRouting` pressed
twice and wheeled without ever releasing; with capture that sequence
means something (a drag in progress), so it now releases. An mcp test
asserts on the wording of a binding-type error, which was reworded to
name `*gooey.Cmd` as well.

Not done: triple click, spatial refinements to the tunnel, and OSC 52.
