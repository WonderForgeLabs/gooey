# Rendering chapter 2: damage-rect flush + graphics in the Composer (epic #21)

Two halves, one epic. Both finish sentences started months of
session-time ago: the render package's "POC note: full repaint every
frame" and the graphics package's Compose-only placements.

## Half 1: damage-rect flushing

The Composer already knows exactly which components repainted; the
wire still gets the whole buffer. Fix at the seam the POC note named:

- `render` keeps a PREVIOUS buffer; flush diffs current against it and
  emits only changed spans (cursor-position + SGR runs per dirty span,
  coalescing adjacent cells sharing a style). Full-frame fallback paths
  remain: first frame, resize, and an explicit invalidate.
- The diff is cell-level truth, not paint-level guess: components
  overpaint their own rects, so comparing buffers catches everything
  including overlap effects — no reliance on the damage counter for
  correctness, only for tests.
- Synchronized-output brackets stay around whatever is emitted.
- Acceptance: byte-count instrumentation in tests — a one-row change
  emits O(row) bytes, not O(screen); a clean frame emits nothing but
  the sync brackets (or skips the flush entirely).

## Half 2: placements reach the Composer

Pixel content (Image, future pixel-chrome components) currently works
only through the one-shot Compose path. The Composer must own
placements the way it owns cells:

- Each paint node may record placements during its Render (the Frame
  API already collects them); the Composer keys placements by owning
  node, replacing that node's placements when it repaints and clearing
  them when it vanishes (Dynamic diff) or turns non-Visible.
- Emission per protocol: kitty uses image IDs — assign per placement,
  delete-by-id (`a=d,d=i`) when a placement is removed or replaced,
  retransmit only on image change; sixel/iterm2 have no delete, so a
  removed placement's cell rect must repaint under it (force-dirty the
  overlapped nodes) before the next frame's placements re-emit.
- Placement changes participate in damage: a frame with clean cells
  and dirty placements still flushes; byte accounting covers both.
- Unlocks (do NOT implement here, just verify the door opens): #81
  pixel-rendered buttons, ColorPicker's pixel tier, browser GIF pixel
  tier. Acceptance for this epic: cmd/demo's Image works under the
  Composer/App path (a new small interactive pixel demo or a demo/
  probe migration), halfblock fallback unchanged.

## Order

Half 1 first (self-contained, immediately measurable), half 2 on top
(its "repaint under removed placement" needs half 1's machinery to be
cheap). Terminal probes stay as they are; no new capability detection.

## Executed

Both halves, as written, with three deviations and one thing the plan
did not anticipate.

**Half 1.** `render.Flusher` holds the previous buffer and emits changed
spans; `Composer` owns one, `Composer.Flush` writes cells then
placements inside a single sync bracket and writes NOTHING when both
planes are clean. Full-frame fallbacks: first frame, dimension change,
`Composer.Invalidate`. Spans coalesce across gaps of up to four
unchanged cells, and SGR state carries across the whole flush since
style survives a cursor move. Measured on an 80×24 tree: full frame 2784
bytes, idle frame 0, a gauge tick 49, a keystroke 34, a focus move 53.

**Half 2.** Placements are recorded through `Frame.Place` and filed
under the executing paint node by a sink the Composer installs around
each node's Render. The per-node diff yields add / move / replace /
remove; `graphics.IDEncoder` (kitty only) splits the emission. Kitty:
`a=T,i=ID` to transmit, `a=d,d=i` + `a=p` to move without re-sending
pixels, `a=d,d=I` to remove and free. Sixel and iTerm2: a removed or
moved placement damages the cells it vacated, and a surviving placement
intersecting the flush's touched spans is re-sent. A full frame re-sends
everything for every protocol. `cmd/demo` now runs on the App/Composer
path with keys for each transition.

**Deviations.**

1. *"Force-dirty the overlapped nodes"* under sixel/iterm2 became
   force-dirty the FLUSH RECT (`Flusher.Damage`). The retained cell
   buffer already holds the correct content for those cells — the image
   was never in the buffer, it was over it — so re-rendering the
   components would produce identical cells at the cost of real damage
   counts. Damaging the flush achieves the same pixels for fewer bytes
   and leaves the paint-level damage guarantee untouched.
2. `Image` was converted from plain fields to properties (`Src`, `Cols`,
   `Rows`). The spec's acceptance ("an Image works under the
   Composer/App path") is not really met by an image that can never
   change: with plain fields nothing dirties the node, so the placement
   diff would have had no input.
3. Placement image identity is `==` under a `recover`, because comparing
   two interface values panics when the dynamic type is non-comparable.
   A panic means "cannot tell", which costs a retransmission and nothing
   else. The alternative was making callers supply an identity key.

**What the plan did not anticipate.** An incremental flush means the
wire no longer contains the screen — "n=2" to "n=3" puts a single `3` on
it — so everything that asserted on the byte stream broke, including the
`\x1b[H` final-frame extraction in `howto-testing.md` and the pty tests
in three modules. `render.Screen` (a terminal model that is an
`io.Writer`) is the answer, and it doubles as the diff's own audit:
replaying the emitted bytes must reproduce the buffer. `testTTY.waitFor`
now polls the modelled screen; `waitForBytes` is the separate helper for
assertions that really are about escape sequences.

Also load-bearing and easy to miss: `App.acquire` now invalidates the
composition's flush. `Raw` enters the alternate screen, which comes back
BLANK after a suspend, a ctrl+z, or a child process — the retained buffer
is right and the screen is wrong, so the flush, not the paint, is what
needs redoing.

**Not built, as instructed:** #81 pixel buttons, ColorPicker's pixel
tier, the browser's GIF pixel tier. The door for them is the
`IDEncoder`/`Frame.Place` pair plus per-node placement ownership: a
component that records placements now damages and repaints like any
other, so those three are ordinary component work rather than pipeline
work.
